## Проекты

1. `frontend`: Админка для базы данных
2. `backend`: Приложение для БД и апи для бота
3. `lib`: Библиотека с шаренным кодом. Включает в себя неймспейсы с API сущностями, которые бэк имплементирует в `typeorm`, а фронт использует при фетче. В том числе там общие для проектов файлы `helpers` и другие функции.

## Установка и конфигурация
> Ожидается сервер с дистром Debian/Ubuntu

#### Mysql и Redis
Сперва необходимо установить и настроить `mysql` (для хранения) и `redis` (для кэша сессий авторизации):
```sh
sudo apt update && sudo install mysql-server redis-server -y
```

#### Создание таблиц в `mysql`
```sh
sudo mysql
```

```sql
CREATE USER 'vera'@'localhost' IDENTIFIED BY 'password';
CREATE DATABASE vera;
GRANT ALL PRIVILEGES ON vera.* TO 'vera'@'localhost';
```

Далее нужно запустить миграции. Более подробно в разделе [Скрипты](#%D1%81%D0%BA%D1%80%D0%B8%D0%BF%D1%82%D1%8B).

```bash
yarn typeorm:run
```

> Для селекта таблиц под юзером Веры можно выполнить следующую команду:

```sh
mysql -u vera -p
```

#### _Опционально_. Конфигурация `redis`

```sh
sudo nano /etc/redis/redis.conf
# supervised no -> systemd
```

### Переменные окружения (Environment Variables)

Далее представлен список переменных среды, управляющий множеством настроек и поведением бота

- `IS_PROD (boolean)`. Передать `true`, чтобы включить. Запуск бота в продакшн режиме. Влияет на настройку проксирования.
- `DISABLE_BOT_LISTENER (boolean)`. Передать `true`, чтобы включить. Отключает ответы бота в чат, но сам функционал не отключается. То есть если true, то метод отправки сообщений бота не вызывается.
- `ADDRESS (string)` - Адрес для app.listen
- `PORT (string/number)` - Порт для app.listen
- `SECRET (string)` - Уникальная строка для сессий

#### Настройки подключения к базе данных

- `DB_HOST (string)` 
- `DB_PORT (string)`
- `DB_NAME (string)`
- `DB_USERNAME (string)`
- `DB_PASSWORD (string)`

#### Настройки апи бота

- `BOT_TOKEN (string)`
- `BOT_POLLING_GROUP_ID (string)`
- `BOT_API_MODE (string)`

#### Настройки админки

> Более подробно про специальные чаты в разделе [Специальные чаты и возможности](#%D1%81%D0%BF%D0%B5%D1%86%D0%B8%D0%B0%D0%BB%D1%8C%D0%BD%D1%8B%D0%B5-%D1%87%D0%B0%D1%82%D1%8B-%D0%B8-%D0%B2%D0%BE%D0%B7%D0%BC%D0%BE%D0%B6%D0%BD%D0%BE%D1%81%D1%82%D0%B8).

- `SETTINGS_CHAT_ID (string)` - Айди чата, в котором меняются настройки для бота
- `DEBUG_CHAT_ID (string)` - Айди чата, в который бот шлет дебаг сообщения
- `ERROR_CHAT_ID (string)` - Айди чата, в который бот шлет сообщения об ошибках
- `AUTH_CHAT_ID (string)` - Айди чата, в котором бот шлет сообщения об успешной авторизации
- `ACCESS_CHAT_ID (string)` - Айди в чата, участники которого могут пользоваться админкой бота.
- `ADMIN_CHAT_ID (string)` - Айди в чата, участники которого видят все чаты бота.

#### Данные для авторизации
- `APP_ID (string/number)` - Айди приложения панели управления ботом. Ссылка есть в разделе [Полезная информация и ссылки](#%D0%BF%D0%BE%D0%BB%D0%B5%D0%B7%D0%BD%D0%B0%D1%8F-%D0%B8%D0%BD%D1%84%D0%BE%D1%80%D0%BC%D0%B0%D1%86%D0%B8%D1%8F-%D0%B8-%D1%81%D1%81%D1%8B%D0%BB%D0%BA%D0%B8).
- `SERVICE_KEY (string)` - Сервисный ключ. Можно взять по ссылке выше.

#### Для фронтенда на этапе сборки
- `VITE_APP_ID (string/number)` - Это `APP_ID`. Но прокидывается на фронтенд для приложения `superappkit` для работы авторизации. **Нужно на этапе сборки фронтенда**.

### Сборка приложений

Далее нужно собрать приложения `backend` и `frontend`. Сделать это можно выполнением команды

```sh
yarn && yarn build
```

или по отдельности командами `yarn build:backend` и `yarn build:frontend` соответственно.

> Фронт админки сервится приложением бэкенда, поэтому разделять их в директории `dist` не нужно. Бэкенд ожидает, что фронт собран и лежит рядом в директории `dist/apps`. Подробнее в `static.module.ts`.

#### _Опционально_. PM2

Можно установить менеджер процессов [pm2](https://pm2.keymetrics.io/). Он предоставляет возможность автоматически перезапускать приложение бота при изменении файлов скрипта, в том числе при краше; удобно читать логи, запускаться при старте системы и тд.

```sh
npm install pm2 -g
```

Конфиг для него лежит по пути `./configs/vera-reforged.config.js`.

## Запуск

Запустить веру очень просто:

### Запуск нодой

```sh
node -r dotenv/config ./dist/apps/backend/main.js
```

Эта команда запускается из корня проекта при условии собранного `dist`. Все настройки и конфигурации можно узнать из файла `./env.example`. После изменения параметров окружения необходим перезапуск процесса `node`, чтоб `dotenv` подхватил корректные значения.

### Запуск через pm2

Необходимо взглянуть на файл `./configs/vera-reforged.config.js`, изменить значения на корректные с точки зрения путей директорий и запустить через `pm2`, при условии, что он установлен, следующим образом:

```sh
pm2 start ./configs/vera-reforged.config.js

# далее проверить можно командой
# pm2 status
# читать логи через
# pm2 logs vera-reforged
```

## Разработка

### Стек проектов

Приложение `frontend` использует `react`, `rtk query` и `vkui`.\
Приложение `backend` использует `nestjs`, `typeorm`, `mysql` и `redis`.

### Архитектура frontend

#### Роутинг

В приложении роутинг завязан на `react-roture-dom`. Все роуты описаны в файле `./apps/frontend/src/app/app.tsx`. Существует два типа роута - `Login` (страница авторизации) и `Content` (скрытый под редиректом при отсутствии авторизованной сессии, т.е. приватный роут). Оба компонента для отрисовки так же расположены в директории `./apps/frontend/src/app/`.

Вложенные роуты прописаны в файле `./apps/frontend/src/components/panels.tsx`. В нем указаны `pathname` адреса, по которому будет отрендерен компонент, сам компонент и кнопки для верхней панели. Так сделано из-за статичной природы `vkui` панели.

#### UI

Все компоненты находятся в директории `./apps/frontend/src/components/`. Компоненты, принадлежащие определенной странице, например duty, расположены в соответствующей директории `<..>/components/duty`. Общие же компоненты расположены в корне директории.


#### Дата слой

Как было упомянуто выше, в приложении используется [rtk query](https://redux-toolkit.js.org/rtk-query/overview). Взглянуть на стор можно тут `./apps/frontend/src/data/store.ts`. Управление данными реализовано через локальные экшены и мутирование значений стейта, а также через фетчинг данных изнутри компонентов. Взглянуть на хуки для фетчинга можно в папке `./apps/frontend/src/data/services/`

#### Обработка ошибок

Эксепшены, которые происходят внутри стора (в диспатче или обработке на бэке), вылетают через миддлвару на уровне стора с кодом и описанием ошибки (если есть), либо с текстом по-умолчанию.

#### Создание нового раздела

1. Добавить в `./apps/frontend/src/components/panels.tsx` новые компоненты раздела, чтобы они отобразились в левом углу основной навигационной панели в приложении.
2. Далее создать редьюсер и сервис с хуками для фетча апи. Апи роуты и типы следует продумать заранее и указать их в файлах `./libs/common/src/lib/routes.ts` и `./libs/common/src/lib/api.ts` соответственно.
3. Ориентироваться можно на существующий функционал и соблюдать общий шаблон написания. 

### Архитектура backend

Приложение следует классическому паттерну [NestJS](https://nestjs.com/) приложения. Весь функционал расположен в одноименных модулях. В директории каждого модуля находится контроллер, сервис, сам модуль и сущности дто и таблица бд.

#### Подключение и настройка БД

Mysql и его настройки расположены в файле `./apps/backend/src/database/database.module.ts`. Так как в приложении используется `typeorm` модуль и шаблон репозиторий, менять ДБ достаточно просто, можно протестировать с `postgresql` или `sqlite`.

> Настройка `redis` для кэширования сессий авторизации происходит в файле `./apps/backend/src/main.ts`.

#### Написание API
1. Исходя из типов апи (`./libs/common/src/lib/api.ts`) необходимо создать `new-module-name.dto.ts` с данными, которые будут приходить с фроентенда.
2. Если новый функционал подразумевает использование БД, то необходимо так же создать `new-module-name.entity.ts` файл и описать в нем новую сущность в бд.
3. Исходя из изменений в файле апи роутов (`./libs/common/src/lib/routes.ts`) необходимо создать контроллер, удовлетворяющий типам из нового апи, используя для этого файлы ДТО из п.1.
3. Далее создать сервис, реалзиующий функционал контроллера. Прокинуть в него подключение к бд и производить нужные изменения над новыми сущностями, используя описание сущностей из файла, созданного в п.2.
4. Далее создать модуль `new-module-name.module.ts`, включить в него провайдер, контроллер и нужные импорты/экспорты.
5. Созданный модуль импортировать и включить в импорты к главному модулю всего приложения в `./apps/backend/src/app/app.module.ts`.

Большая часть скриптов понятна и в дополнительном описании не нуждается. Но про некоторые все же стоит написать.

### yarn tsc

Скрипт позволяет проверить сходимость типов во всех приложениях сразу. Пусть изменение проводилось в `./libs/common/`, его изменение до коммита будет проверено на уровне использования в других приложениях.

### yarn typeorm:*

## Особенности бота

### Авторизация

Устройство авторизации завязано на несколько факторов.
1. Вход пользователя через аккаунт ВКонтакте.
2. Получение и обмен токена юзера поход с ним в апи метода `users.get`.
3. Далее проводится проверка на наличие пользователя в специальном чате. О таких чатах будет подробно рассказано далее.
4. После прохождения проверки пользователю откроются чаты, в которых он и бот одновременно состоят. При не прохождении проверки у пользователя отобразится, что у него нет доступа.
5. Эта проверка полностью динамическая и производится на каждый заход, ввиду чего не требуется перезагрузок или ожиданий между добавлением пользователя в чат и его последующей успешной авторизации.

### Специальные чаты и возможности

Всего у Веры следующее количество специальных чатов (они не выдаются в списке чатов бота в панели управления). Во всех чатах ниже бот должен состоять и иметь права администратора.

- `ACCESS_CHAT_ID` - Чат, в котором необходимо состоять пользователю, чтобы иметь доступ к панели управления ботом.
- `AUTH_CHAT_ID` - Чат, в котором Вера дублирует лог об успешной/неуспешной авторизации **каждой** сессии.
- `ADMIN_CHAT_ID` - Чат, в котором необходимо состоять администратору панели управления, чтобы бот выдавал все чаты, которые есть у бота, а не только общие чаты (чаты, в которых состоит пользователь и бот одновременно).
- `DEBUG_CHAT_ID` - Чат, в который Вера дублируют дебаг сообщения о своей работе - дежурные, кроны и тп.
- `ERROR_CHAT_ID` - Чат, в который Вера дублирует критические (и не очень) ошибки выполнения.
- `SETTINGS_CHAT_ID`  - Чат, в котором по задумке (функционал не реализован) можно контролировать возможности бота - аналог feature toggles в ВК.
